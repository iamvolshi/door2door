# Platform Limitations & Technical Roadmap

This document details the architectural boundaries of the MVP release, known system limitations, and prioritized development phases for subsequent rollouts in Cox's Bazar and the Chittagong Division.

---

## 1. Current MVP Limitations

1. **Geospatial & Road Mapping**:
   - OSRM route calculations use standard road graphs; beach sand trails, pedestrian alleys, and temporary road blocks in Cox's Bazar during tourist festivals require driver manual navigation adjustments.
2. **Offline Mode for Delivery Riders**:
   - Mobile web app requires active 3G/4G cellular coverage (Grameenphone/Robi/Banglalink). Order details are cached in local browser storage, but status transitions require internet reconnect.
3. **Payment Settlement**:
   - Real-time instant disbursement to driver personal bKash wallets is currently processed through batched payout scripts rather than fully automatic bKash B2C API integration.
4. **Multi-Store Batched Checkout**:
   - Customers currently place orders per merchant. Multi-merchant cart ordering in a single checkout is scheduled for Phase 3.
5. **Registration Onboarding Gap**:
   - Closed for account setup. A self-registered customer can save, edit and remove their own delivery addresses (`/addresses`) and order without naming one; a merchant application carries the shop address, and approval creates both the account's `merchants` record and the address it points at; a rider approval creates the `rider_profiles` row (NID, vehicle, optional licence and zone, `dutyStatus` starting at `OFF_DUTY`). Approval and profile creation are one transaction, so a store that cannot be built leaves the account `PENDING` rather than permitted-but-inert. What remains is the working life of those profiles: a merchant's shelf is now its own (below), but nothing yet assigns an order to a rider, and no merchant-facing route moves an order through its states.
   - Closed for the merchant's own profile. The onboarding answers became a store at approval and were then frozen, so renaming a shop, correcting its description, moving it or closing it for the day all needed an administrator and a database. `GET`/`PATCH /merchant/profile` (`merchant:manage:own`) now make the shopfront the merchant's: name, description, category, opening state and shop address, with the store found by the account that owns it rather than by an id in the path. Closing is a real switch — the order path already refuses a store that is not open, so it stops taking work the moment it is set. The address is edited in place, so orders and riders already pointing at the shop still do. What is refused is refused by name rather than ignored: the trade licence is unique platform-wide and licensing is an administrator's decision, the phone is the number the account signs in with, and the rating belongs to the customers who gave it. Each change is one transaction and one `MERCHANT_PROFILE_UPDATE` audit row carrying the profile before and after, which is what makes "where was this store when the order was placed?" answerable.
   - Closed for opening one. The store itself still had to arrive from an approval, so an approved merchant with no `merchants` row had a `404` from both routes above and nowhere to go from there. That state is one this API cannot produce — approval writes the store in the transaction that approves the account, so a store that cannot be built leaves the account `PENDING` rather than permitted-but-inert — but a migration, a restored backup or a hand-edited table can, and the account holding it held a grant it could not spend. `POST /merchant/profile` now opens the caller's own store: the name on the sign, the licence, an optional category, description and opening state, and the shop address a store cannot exist without, parsed by the very rules an approving administrator's address goes through. Ownership is the token, so `ownerUserId` is never read from the body and there is no id to point at somebody else's shop; `phone` and `rating` are the platform's, taken the way approval takes them, and sending either is a `400` naming it. The licence is **required** here and **refused** by the edit, which is not a contradiction: a store cannot exist without one and stating it once, at birth, is exactly what registration asks for and checks for uniqueness, while changing which licence a store trades under is a licensing decision an administrator makes. The store, its shop address and a `MERCHANT_PROFILE_CREATE` audit row are one transaction, so a refused store is never an orphaned address row, and opening a second store for one account is a `409` naming the one it already has rather than a duplicate row — the check is inside the transaction, which `BEGIN IMMEDIATE` serialises against a racing caller. A merchant's self-service store is the same shape approval produces, deliberately: category defaulting to `General`, `isOpen` to `true`, the address labelled `Shop` and not PII-restricted, so nothing downstream can tell which of the two paths built it.
   - What remains is that a store can be opened but never closed, and that nothing reads a licence. There is no way to delete or retire a store: `isOpen` is the day's trading switch, not a door out of the platform, so a merchant that ceases trading keeps its rows, its catalogue and its orders for good — the same conservatism that keeps the row of an address an order was delivered to, and for the same reason, though that row can at least be taken off its owner's own list (below), which is a door a store has no equivalent of. The licence is checked for uniqueness and nothing else: it is stored as the merchant typed it, never verified against any licensing register, and it has no expiry, no suspension short of suspending the whole account, and no way to be corrected by the merchant — a typo in it is an administrator's job, which is a deliberate consequence of the decision above. The create body's `address` is not run through the service-area check a customer's delivery address now is, which is consistent with approval and with what a shop address means — riders collect from it, they are not sent to it — but it does mean a store can be opened outside every serviced zone and simply take no orders. There is also no `DELETE`, no way to hand a store to a different owner, and no list of stores for a merchant that has somehow ended up with two.
   - Closed for the catalogue. A newly approved store began empty, and an empty catalogue is a store nothing can be ordered from at all — `POST /orders` answered `404 Merchant catalog` before it priced anything. `GET`/`POST /merchant/catalog` and `GET`/`PATCH`/`DELETE /merchant/catalog/:itemId` now make the shelf the merchant's, under `catalog:manage:merchant` — a grant declared in `rbac.ts` and, until now, held by nobody's reachable route. The store is found by the account that owns it and every item belongs to it, so an item id belonging to another store answers `404` rather than confirming what that store sells. What the merchant cannot set is refused by name: `id` and `sku` are the platform's — `sku` is `UNIQUE` across every store, so a self-service one would let the first store to claim a string keep every other store out of it, and a generated `CXB-…` is issued instead — and `merchantId` is not a field because the store comes from the token. Prices are refused rather than rounded (`12.345` is a `400`; money is rounded to poisha everywhere else, and telling a merchant a price the customer will not pay is telling them something untrue), zero is refused because a giveaway is a coupon, and a picture may only be an `http(s)` URL because it is other people's browsers that fetch it. An item a customer has already ordered cannot be deleted (`409`, naming the sold-out switch that does what the merchant meant) because the order line keeps pointing at what was bought. Every accepted change is one `CATALOG_ITEM_CREATE`/`_UPDATE`/`_DELETE` audit row carrying the item before and after. And the loop closes: the first item is what turns an approved account into a store that can take an order, which is tested all the way through the order path.
   - What remains is the rest of a menu. An item's stock or portion count is not expressible: the pricing engine honours a `maxQuantityPerOrder`, but no column stores one, so a merchant cannot say "two per customer". The SKU is issued and cannot be revised, and a rejected one is a dead end rather than a request for a different string. There is no image upload — the merchant points at a URL they host elsewhere, so a shop with no hosting has no pictures. Items cannot be categorised into sections beyond the one free-text category, nor ordered deliberately within a category (the list is alphabetical for both the merchant and the storefront). Modification options are not modelled at all: "no onions" is free text on the order, never a priced choice on the item. The catalogue is also unpaginated and capped at 200 items precisely because of it, and a bulk price change — the thing a merchant actually wants on a busy morning — is one request per item.
   - What remains there. The audit row records the store's location but no history of it, so the trail shows each change and not the state at an arbitrary past instant. And one hole is inherited rather than introduced: the shared address rules treat an empty string as a valid "clear this field" (`services/addressRules.ts`), which the shop profile now refuses for `streetAddress`/`area`/`district` but customer addresses still allow — a customer can blank the area of a saved address with `PATCH /addresses/:id`, and an order placed against it is one a rider would have to guess at.
   - Closed for the fleet's reach, at the door. The ten pilot zones were configured with bounding boxes, per-zone restrictions and a status, and nothing consulted them: `ServiceAreaManager` was instantiated at boot and asked nothing, so a customer could save an address in Dhaka with coordinates on it and the platform agreed to deliver there — the coverage rule existed, was described, and had no bearing on what the API accepted. `POST /addresses` and `PATCH /addresses/:addressId` now put a supplied coordinate pair through it (`src/services/serviceAreaRules.ts`), and a point in no zone, or in a zone the platform has suspended, is refused with a `400` whose details carry the zone it landed in (`null` when it landed in none), the pair itself, and the manager's own reason — so "we do not go there" and "we are not going there this week" are different answers to a customer rather than one. The rule is asked rather than reimplemented, which is why suspending a zone, redrawing a box or adding a restriction changes what the API accepts without a second copy of the geography being kept beside it; `RESTRICTED` is not refusal, so Saint Martin's Island stays orderable through the maritime window the manager describes, and the nearest-centre fallback is inherited rather than tightened, so an address outside every box but inside the fleet's reach is still saved. The check runs before the write, so a refused address leaves no row and does not take the default from the address it would have replaced.
   - What remains is the half coordinates cannot cover, and the order path. An address saved without coordinates cannot be judged by this gate, and coordinates are optional everywhere they are accepted — so an order can still be placed to a saved address that nothing has checked, and the pilot's seeded rows and any address written before this rule existed keep whatever they had. The zone *text* is not cross-checked against the coordinates either: an address whose `area` says Kolatoli and whose coordinates say Dhaka is saved on the coordinates' word, because coordinates are the only input that names a point. Nor does the order path consult coverage at all: `POST /orders` takes a `deliveryAddressId` plus a client-supplied `serviceArea` and `distanceKm`, and the pricing tier is chosen from that string rather than from where the address actually is, so the same rule would have to be applied at order time to make "customers cannot order to places the fleet cannot reach" true of every row rather than of the ones that carry a pair. There is also no read for the coverage itself: a client cannot ask whether a point is served before saving it, and no route serves the zones, their windows or their restrictions — the only signal is a refusal.
   - Closed for duty state. A rider profile is created `OFF_DUTY` by approval and now has an owner: `GET`/`PATCH /drivers/me/duty` under the rider's own grant (`rider:duty:own`), over the schema's own four states, with `AVAILABLE`, `ON_BREAK` and `OFF_DUTY` settable by the rider and `ON_DELIVERY` refused because dispatch owns it. Asking for the state you are already in is answered (`changed: false`) rather than refused, and a rider carrying a delivery cannot leave the roster at all — the guard is in the write statement (`WHERE dutyStatus <> 'ON_DELIVERY'`), so a dispatch assignment cannot be raced. The pilot's seeded driver gained the rider profile the seed had omitted, which is what left the one rider the pilot has unable to hold a duty state. Dispatch's half is a read: `GET /drivers/roster` (`rider:read:all`, administrators) lists the working riders ordered so the ones who can take work come first, with the vehicle and phone a dispatcher needs and without the identity documents they do not; a suspended account is off it in every state, and the profile row survives so reinstatement restores the rider where they were.
   - What remains is everything around it. A duty change is a shift event, logged but not written to `audit_logs`, so there is no history to answer "was this rider on duty at 18:40?" — that needs a shifts table or an audit entry per change, and neither is here; the profile's `updatedAt` is the only trace, and it holds one timestamp. `ON_DELIVERY` is still unreachable through the API, because nothing assigns an order to a rider yet, so the state that guard protects is one only a direct database write can produce (which is how it is tested). A rider cannot be taken off duty by an operator: suspension is the only lever, and it ends the account rather than the shift. And the roster is a bounded page (default 200) with no cursor, so a fleet larger than that is read in whatever order the limit cuts it.
   - Closed for the rider's own list of deliveries. A rider could be put on the roster and given a duty state, and the one thing that made the roster worth joining — the deliveries assigned to them — was invisible in the API: `orders.driverId` was readable by nobody, so a rider had to be told where to go out of band. `GET /drivers/me/orders` (`order:read:driver`, the rider grant that `rbac.ts` had declared since the beginning and that until now no reachable route used) lists the caller's own deliveries newest first, one page, with `?status=` narrowing to a single state and `?limit=` bounding the page (default 100, max 200; both refused by name when they are values the platform does not have). Ownership is the query rather than a check before it — `driverId = <the token owner>` is the only `WHERE` on the only statement — so there is no id in the path to guess, and an order nobody has accepted, or one assigned to another rider, is not merely hidden from an entitled rider but absent from the answer entirely; the delivery address and the store's name are joined onto the order in that same read, so a rider's list is one statement whether it holds one delivery or two hundred. The delivery address is served through `maskAddress`, the platform's one rule for who may read a client's door, carrying the viewer's role and the fact that the order is assigned to them — the branch that rule already defines as full — so the rider reads the street they are delivering to, and the rule is asked rather than reimplemented, which is what makes a later change to it a change to this route. The customer's internal account id is never handed to the rule and so cannot appear in the reply: the rider is told which door and which store, and not who the customer is. The customer's note for the door (`orders.specialInstructions`) travels as the address's own `deliveryInstructions`, which is what makes it exactly as visible as the address it belongs to and no more.
   - What remains there is the assignment itself and the rest of the rider's day. Nothing in the API puts an order into a rider's hands: `orders.driverId` is still written only by the seed and by tests, so this is a read of assignments dispatch makes outside the platform, and `ON_DELIVERY` is still reachable only by a direct database write. `order:accept:driver` and `order:update:driver` are declared and held and still serve no route, so a rider cannot accept an offer, refuse one, mark a parcel picked up or confirm it delivered, and there is no proof of handover at all. The list is a bounded page with no cursor and no date window, so a rider with more history than the page holds reads it in whatever order the limit cuts it, `?status=` is the only filter (there is no "today"), and nothing on it is a location: no distance, no map, no live position for the customer watching.
   - Closed for the address a delivery was sent to. `DELETE /addresses/:id` refused one an order had been delivered to with a `409`, because the order row points at it — so the address a customer has most reason to be rid of, the one they no longer live at, was the one they were stuck with. It is now two things at once. The order keeps its own copy of where it was sent, taken at placement (`orders.deliveryAddressSnapshot`: label, street, area, district, postcode and coordinates), and the row is *detached* (`addresses.removedAt`) rather than deleted — gone from every listing, default lookup and count, `404` by id for reads and edits, unusable as an order's destination, and left on file only as what those orders say they were sent to. The filter lives in the statements rather than in each handler, which is what stops an address coming back to somebody who removed it — including `updateOwned`, so a detached row cannot be edited back to life. The reply names which of the two happened (`outcome: DELETED` or `DETACHED`, with `ordersKeepingIt`), a detached address frees its place in the ten-address cap, and losing the default still promotes the next newest whether the row went or merely left the list. Reading an order reports `deliveryAddress` beside `deliveryAddressId` — to the customer it was delivered to and to a role holding `pii:read:full`, not to the store, which reads its sale without the customer's door — preferring the copy on the order over the row it names, so correcting or retiring an address can no longer rewrite where a finished delivery went. Both columns reach an existing database through `MIGRATION_STATEMENTS`, which is tested by dropping them from a migrated one and migrating again.
   - What remains is the orders that predate the copy, and what a detached row is. There is no backfill, deliberately: an order placed earlier falls back to the address row, which is what it reported until now, so editing that address still rewrites what such an order says about its own delivery — the snapshot protects the orders placed after this ships. A detached address is invisible to everybody through the API, its owner included: nothing lists it, nothing restores it to the list, and no operator view serves it, so the only way to read one is a database query. Nothing un-detaches either, so a customer who removes an address and then wants it back saves it again as a new row with a new id — which will not be the id the old orders name. Two addresses that look identical can therefore have different fates, depending on whether anything was ever delivered to them: one is deleted outright, the other kept forever. The rider's delivery list still reads the live row through `maskAddress` rather than the order's copy, so a rider looking back at an old delivery sees the address as it stands today rather than as it was carried to — the same reader that makes a rider's list work is the one that could not be switched to the snapshot without giving a rider a record of an address that may have since been corrected.
   - Closed for the data-entry half, and visible before it is attempted. An approval can fail for a reason nothing in the queue mentioned: an application filed before merchants had to state a shop address, a row with no rider identity on it, or a licence another store has since taken. Each of those answered `400`/`409` only when an operator spent an approval on it. `GET /admin/registrations` now judges every application it returns (`readiness.approvable` plus a `blockedBy` list, each entry naming the same `field` the refusal names, whether the approve body can carry it, and what to do when it cannot), and `?approvable=false` is the worklist of the ones that would fail. For the two blockers a reviewer can clear — a shop address, and a rider's NID or vehicle — the approve body now accepts the missing piece (`address`, or `rider.nidNumber`/`rider.vehicleType`/`rider.licenseNumber`, each field independent), which is what turns a flagged row into an approved one over a phone call. What the reviewer typed is recorded on the audit row as field names under `suppliedByReviewer`, never as values.
   - What remains is that a flagged application is not always fixable, and the queue says so rather than implying otherwise. A trade licence already held by another store cannot be resolved by approving anything: the operator rejects it, and the applicant cannot re-file the same number, because registration refuses a phone number that already has an account — so a rejection there is the end of that account rather than a request for documents. There is no document-request state at all (the legacy `AdminService` names a `DOCUMENTS_REQUIRED` status, but it is in-memory, unreachable from these routes, and unused): an application that cannot be completed is rejected or left pending. The readiness judgement is also assessed per request rather than stored, which is deliberate — an account can gain a blocker without its own row changing — but it means the worklist is a snapshot: a licence taken between the read and the approval still fails at the approval, where the conflict is caught by the transaction. Finally, the queue reads a bounded page (default 100, `possiblyTruncated` says when more may match), and readiness is assessed for exactly those rows.
6. **Access Token Revocation**:
   - Closed. Access tokens are no longer stateless: each names the session that minted it, and a bearer request is refused unless that session row is still live, so reuse detection, rotation and logout retire the access tokens they issued on the spot instead of leaving a 15-minute tail. The cost is one primary-key lookup per authenticated request (0.016 ms measured against the SQLite store), cheap enough that the access-token TTL does not have to be shortened to limit exposure. Two consequences worth knowing. First, an access token is now only valid against the database that holds its session, so a deployment whose processes do not share one database (see item 8) will refuse tokens minted elsewhere. Second, a token that names no session — anything minted before this binding existed — is refused rather than grandfathered, so clients re-authenticate once when the change ships. Logging out still ends only the session it names; ending all of them at once is the bullet below.
   - Closed for the owner's own view and their own panic button. `POST /auth/logout` ended the one session it named, and nothing could answer "where am I signed in?" — so the ordinary fear (a phone left in a taxi, a shared laptop, a token read over a shoulder) had no self-service answer, and only a stolen-chain replay would sign anybody out. `GET /auth/sessions` lists the account's live sessions newest first, one entry per *login* rather than per rotation (a refresh retires the row it replaces, so a chain of exchanges is still one device), with the address and device string the login was recorded from, and `isCurrent` marking the session the request came through. `POST /auth/sessions/revoke-all` ends every one of them, the asking session included, and says so in the reply (`currentSessionRevoked`) instead of leaving a client to discover it on its next request; the access tokens that asked and every refresh token the account holds are refused from the next call on. `revokedSessions` counts sessions that were genuinely live — an expired row is retired with the rest but not counted — and the read and the write share one transaction, so a login racing the call is either ended or left alone and never half-counted. `DELETE /auth/sessions/:sessionId` cuts it down to one device, which is the decision the list makes possible: a phone left in a taxi is not a reason to sign the owner out of the laptop they are working on. The session named has to be one of the caller's own, and that is enforced inside the `UPDATE` rather than by a read before it, so nothing can move between the check and the write; a session belonging to another account, an id that names nothing, one this account already ended and one whose refresh token has run out are all answered "no live session" with the same body, because telling them apart would turn a session id into something worth guessing. The revocation and its `SESSION_REVOKED` trail row are written in one transaction, and that row names two different sessions on purpose: the one it ended, and — in `sessionId` — the login the request came through, so "which of my devices ended that one?" is answerable. A reply carries `currentSessionRevoked` so a client can tell "I ended that other phone" from "I just signed this one out". None of the three routes carries a permission, deliberately: the rows are the caller's own, narrowed by the token's user id, and an account still awaiting review holds no permission at all yet may hold a handset it no longer trusts — the one security action that must never depend on a grant somebody else controls. The listing selects its columns explicitly and types them as `AuthSessionView`, which has no field for the refresh-token digest, so "the session list returned the credential" is a compile error rather than a review catch. The two ending routes write `SESSION_REVOKED` or `SESSIONS_REVOKED_ALL`, or nothing: an attempt that ended no session is not audited, as elsewhere in the API — the trail records what happened rather than what was tried. `SESSIONS_REVOKED_ALL` is one `audit_logs` row naming the session ids it retired. Reuse detection still ends one family and warns the owner; this ends all of them and deliberately does not, because a notice exists to tell somebody about something they probably did not do, and waking their phone to confirm a button they just pressed would train them to ignore the channel that matters.
   - What remains is anything that acts on what the list shows. The list is a snapshot with no `lastSeenAt` and no rotation history — a session's `createdAt` is when that login happened and its `expiresAt` is seven days after, so nothing here answers "is this device still being used?" or "has it refreshed since?". Sessions are never deleted, only revoked or redacted (item 15), so the account's row count grows with every login it ever made and nothing prunes it; the listing filters by liveness, which keeps the *answer* bounded but not the table. And a revoked-because-signed-out row is indistinguishable from one retired by rotation, logout, a burned family or a suspension — `isRevoked` is one flag for five reasons, so an operator reading the table cannot tell why.
   - Closed for the trail. The session id was known to the server and then thrown away: the middleware checked it on every request and nothing wrote it down, so `audit_logs.userId` answered "which account" and the next question an incident asks — which of that account's logins did this — had no answer at all. One login is now a first-class subject of the trail. Every audit row written by an authenticated request carries `sessionId` (order placement, a merchant's profile and catalogue changes, payment, cancellation and refund rows, an administrator's approval, suspension and reinstatement, the session controls themselves, and the session that presented a replayed refresh token), the column is indexed because "what did this session do?" is the query it exists for, and the rate-limit counter row — which runs before authentication by design, so a flood is refused before it can cost a token check — is named with the session once the bearer token has been proved. The name is read for free out of the increment's own `RETURNING`, which is what makes it one write per device per window instead of one per request: measured against the pilot's SQLite store, the widened counter statement is 0.646 ms against 0.632 ms without the session column (5,000 counted requests on a hot row), and the attribution write is 0.016 ms, guarded by the window so a counter that has just rolled over is never stamped with the device that was using it. The key is deliberately unchanged: the limit is still one budget per client address, because a client that could buy a fresh allowance by signing in again would make the limit meaningless — the session id is the name beside the count, not a second key. Nothing is backfilled on existing rows: `NULL` means no session was involved, which is a different fact from "the session is unknown", and a guess would be indistinguishable from an answer.
   - What remains is that nobody can read it through the API. The columns are written and indexed, and the operator views that exist (`GET /admin/security-notices`) read the notice trail, not `audit_logs`; a "what did this session do?" endpoint would need the `audit:read` grant pointed at the audit table itself, and there is no such route. Several paths that know a session still do not record one: the notice-delivery rows (`SECURITY_NOTICE_SENT`/`_FAILED`) are written by the channel that carried the warning rather than by the request that caused it; `POST /auth/logout` revokes the session named by its refresh token but writes no audit row at all, so the one self-service session end that does write one is `revoke-all`; and a rotation writes no row either, so the trail shows a session's first sight and its last, not the exchanges in between. The rate-limit row names the *last* authenticated session of the window rather than all of them, so two logins behind one address (an office, a NAT) are indistinguishable once the second one has been counted — the audit rows still separate them, which is why the counter is the weaker of the two records. And a session id means nothing to an operator without the row it belongs to: it resolves to an address, a device string and a created-at time only until item 15's window closes, after which the trail says which login acted and no longer where it was.
7. **Request Rate Limiting Is Shared by the Deployment**:
   - Closed. The counter was a map in the memory of whichever process served the request, so `RATE_LIMIT_MAX` meant "per process": two processes behind a load balancer allowed twice the configured burst from one client address, three allowed three times, and a restart forgot the window it was in the middle of. It is now a row in `request_rate_limits`, keyed by the client, and the increment is one atomic statement (`INSERT … ON CONFLICT … RETURNING`), so the number in the configuration is the number the deployment enforces. Verified across processes sharing one database, in two layers. Two servers inside one process cover the arithmetic and the rollover: twenty concurrent requests split across both are answered with exactly the limit's worth of `401`s and `429`s for the rest, and a window that closes lets both serve again rather than each opening its own. The same file (the real-process section of `tests/rateLimitAcrossProcesses.test.ts`) then boots the built API **as two separate processes** — `node dist/main.js`, separate PIDs, one shared file — where the fourth request is refused *between them*, including by the process that had served only one, and the shared window opens for both at once. The counter is read back out of the platform database afterwards: one row, every request counted including the refused ones, and a 32-character digest for a key rather than the address. That second layer is the one that can fail: an in-process pair cannot tell a shared counter from a per-process one, because both servers share a PID — a per-process key turns the fourth request back into a `401` in the real-process section and nowhere else. The login limiter and this one are now the same kind of thing; `otp_challenges` was already database-enforced.
   - What it costs, measured rather than assumed: **0.78 ms per counted request** against the pilot's SQLite store (5,000 calls through the built API code, 0.76 ms when every request is a different client rather than one hot row). That is a write per request — the same order as the price of a shared count, and roughly fifty times the primary-key session lookup every authenticated request already makes (0.016 ms, item 6). It is affordable at pilot volume and it is a real ceiling to watch as traffic grows; if it ever binds, the two levers are counting coarsely (flush per-process increments on an interval, trading exactness for writes) or switching the driver to `synchronous=NORMAL` under WAL, which is faster and can lose the last transactions on power loss — neither is done here, because the guarantee above is worth a write and the durability of orders is worth more. The row holds a keyed digest of the client address rather than the address, because a table written by every request is the last place that should accumulate where customers live; the digest is derived from `ENCRYPTION_KEY`, so every process computes the same key — a random per-process salt would have given each process its own counter and brought the multiplication straight back. Rotating that secret starts every window afresh, which is harmless: the worst it can do is hand one client a fresh allowance once.
   - Limits that remain. The window is still *fixed*, anchored to the first request that opened it, so a client can spend its allowance at the end of one window and again at the start of the next; that boundary burst is unchanged, and closing it means a sliding window rather than a durable one. The table is not in item 15's retention sweep because it never holds an address; rows are deleted once their window closes (their value cannot be read again), so it holds the clients seen in the last window and nothing older. And the limiter fails *open*: a counter that cannot be consulted allows the request and logs the first failure, because a database blip must not become a blanket `429` from an abuse control — so a database outage removes this limit while leaving authentication intact. Which address is counted at all is settled separately in item 14, and still matters behind a proxy.
8. **Shared Database Is Required for Multiple Processes**:
   - Closed for the multi-host case, with an engine rather than a file. `DB_DRIVER=postgres` runs the same repositories, the same schema and the same statements against a server, reading `DATABASE_URL`; `sqlite` stays the default, so nothing moves unless a deployment says so. The choice is explicit and not inferred from the URL being set, because `DATABASE_URL` has a default — treating "a URL exists" as "run on PostgreSQL" would move a deployment off its own database the first time somebody exported one.
   - One translator, not a second schema. Everything the platform writes is written once, in the dialect SQLite speaks, and `src/db/sqlDialect.ts` rewrites each statement on its way to PostgreSQL: `?` becomes `$1`, `ADD COLUMN` becomes `ADD COLUMN IF NOT EXISTS`, `x COLLATE NOCASE` becomes `lower(x)`, `INTEGER` becomes `BIGINT` (64-bit, so the epoch milliseconds in `otp_challenges` and `request_rate_limits` do not overflow in 1970) and `TEXT` is pinned to the `"C"` collation, which is what SQLite's default BINARY comparison is — a locale collation would have made `'2026-1…' < '2026-10…'` and id ordering depend on the server. The rule the port actually turned on was identifier case: PostgreSQL folds an unquoted identifier to lower case, so `sessionId` would have been stored as `sessionid` and `SELECT *` would have handed the application a row whose key is `sessionid` — `row.sessionId` undefined, `Boolean(undefined)` false, and every camelCase field silently blank, which is exactly how the first run of the new test suite failed. Every mixed-case identifier is quoted now, in the DDL and in the statements alike, so column names and row keys keep the spelling SQLite preserves. `BIGINT` is also parsed back into a JavaScript number for the same reason: a row that arrives with `isActive` as the string `'1'` would read as `true` while `'0'` also reads as `true`.
   - The per-request session lookup is still one indexed read, which is the cost every authenticated request pays. `SELECT * FROM auth_sessions WHERE id = ?` becomes one parameterised statement, and `EXPLAIN` on it is an `Index Scan` on `auth_sessions_pkey` with no sequential scan anywhere in the plan. Measured through the repository on a real server: **0.97 ms** median at 5,000 sessions and **0.95 ms** at 50,000 (200 lookups each, warm, vitest against a Docker PostgreSQL on the same machine — the round trip dominates an index read that small, which is why the number is flat rather than tiny). Ten times the rows for the same read is the claim, and a scan would not have been flat.
   - Writer serialisation survives, because the invariants were written against it. `BEGIN IMMEDIATE` in SQLite serialises every writer; PostgreSQL under READ COMMITTED would let the check-then-write paths — a refund that may not exceed what was paid, one `Idempotency-Key` claimed once, one refresh token rotated once, the first-boot seed — interleave, and no row lock protects a read that decides a later write. Every transaction therefore takes a transaction-scoped advisory lock before its callback runs, which is released by `COMMIT` or `ROLLBACK` and gives exactly the guarantee the code was written against. Verified by racing two transactions that read a counter, wait, and write it back: both apply (`1` then `2`), where a lost update would have left `1`. Connections are released exactly once on every path, which is a failure mode worth naming because it is silent: a transaction that leaked its connection worked until the pool was empty and then waited forever, and the suite now runs six concurrent transactions against a pool of two so that cannot come back.
   - Concurrent boots are handled on both engines: SQLite's driver waits up to five seconds for another writer's lock instead of failing, migration retries briefly when the file is busy, an already-added column and an object another boot created a moment ago are both read as "already applied" rather than as faults, and the first-boot pilot seed runs inside a write transaction so two processes starting at once cannot both seed. Verified by starting two processes on an empty database and logging in across them.
   - What remains. Nothing rehearses the schema change: the API creates and migrates its own tables at boot, which is what makes a one-command deployment possible and also means there is no reviewed migration step, no dry run and no rollback path for a deployment that ships a schema change. The write lock is deployment-wide, so writes serialise exactly as they did on one file — correct, and a ceiling on write throughput that lifting would require redesigning those two invariants around row locks or serializable isolation with retries. `DATABASE_URL` and `DB_DRIVER` are read at boot and are not reloadable; there is no read replica or read/write split, so reads scale with the pool rather than with the deployment; and TLS is whatever the connection string asks for (`sslmode`), with no separate CA configuration. Finally, the PostgreSQL suite is only proof where a server is reachable: it creates a schema of its own and drops it, and when nothing answers it skips loudly rather than passing quietly — a checkout with no PostgreSQL therefore does not exercise this path by default.
9. **Security Notices No Longer Depend on SMS**:
   - Partly closed. A burned session family is still reported by SMS, through the same provider, credential and retry policy as login codes — and that channel still fails exactly as phone login does with `SMS_PROVIDER` unset (or `SMS_MOCK_MODE=true`), where nothing leaves the building and `audit_logs` records `SECURITY_NOTICE_FAILED` with `code: SMS_NOT_SENT` rather than implying the owner was reached. What changed is that the warning no longer *depends* on it. A notice is written first as a row in the account's own list (`notifications`), on the incident path, before the `401` is answered, and `GET /api/v1/notifications` hands it back to whoever signs in with that account. Both of the SMS channel's failure modes are therefore covered: no provider configured, and a notice lost to a hard kill — the durable row is already committed and only the text is lost. The cost of that half, measured against the pilot's SQLite store: **0.68 ms to store one notice**, 0.157 ms to read a page of the list with its unread count, and the reuse-detection `401` itself goes from 2.55 ms to 3.87 ms per replay (400 replays, a path that already revokes a family and writes two audit rows). An operator can now see all of it: `GET /api/v1/admin/security-notices` (requires `audit:read`, read-only) lists the notices with the outcome the channel wrote back onto each one — `DELIVERED`, `FAILED` with the provider's own code, or `UNKNOWN` when no attempt ever reported — plus the account it belongs to, a derived `followUp` flag that is true only while neither channel reached the owner, and a `lockedOut` flag taken from the account itself — so `?followUpOnly=true&lockedOutOnly=true` answers the one question that has to be acted on now: an owner who cannot sign in to read the list *and* was not reached by text. The two are separate because an unreached warning on a working account can still be read at the owner's next sign-in, while on a suspended account it cannot be read by anybody until an administrator reinstates them; and `lockedOut` is derived per request rather than stored, because suspension and reinstatement both happen after the notice is written. The outcome is stored on the notice rather than reconstructed from `audit_logs`, because a burn can happen twice for one family (a further replay of a burned chain is refused, and refused again), and joining two growing trails on the incident would have multiplied the rows an operator is supposed to read.
   - The same two channels now carry every event worth a warning, not only a burned session: `PHONE_CLAIMED` when an account is created for a number (raised on the account-creation path, so every route that creates one warns once), `REGISTRATION_REJECTED` when an administrator refuses an application, `ACCOUNT_SUSPENDED` when an account is deactivated, and `SESSION_REVOKED` as before. The vocabulary and both channels' wording live in `SECURITY_NOTICE_COPY`, and bodies are held to a single SMS segment by test, so the text and the list entry cannot drift into telling the owner different things. The administrator's own words — a rejection reason, a suspension reason — are kept in the notice's `details` and in `audit_logs`, never in the message: a warning that needs no reply should not be carrying an operator's phrasing to a customer. Suspension and reinstatement are one transaction each, so the deactivation and the sessions it retires cannot drift apart, and the operator view gained a `type` filter so the three kinds can be read separately.
   - What remains is follow-up, not visibility. Nobody is paged: the view is passive, so an unreached customer is discoverable but not escalated, and an operator has to remember to look — an alert when `followUp` — or, more sharply, `lockedOut` — is non-zero is the obvious next step and nothing in the flow would have to change. `UNKNOWN` deliberately does not say whether the attempt never started or its outcome was lost, since neither is knowable from one row. An email channel would still reach the owner out of band and needs a provider plus a real address, and accounts with no email are stored with a placeholder that delivers nothing. The SMS attempt remains best effort in timing. And the notice names the incident but not the device or address the session was signed in from, so it says what happened and not where. Two limitations belong to the wider vocabulary specifically. A suspended account cannot read its own list, because it cannot hold a session at all — by construction the suspension notice is read after reinstatement, so an owner who is suspended and never reinstated is reached by text or not at all, which is exactly the account the `followUp` worklist now shows an operator. And nothing prunes `notifications`: unlike the OTP trail's 30-day sweep, one row per incident stays forever, and that trail now grows with registrations, refusals and suspensions as well as with burns, so a long-lived deployment accumulates a security history nobody has decided how long to keep.
10. **Order Idempotency Is Now Durable, With a Window**:
   - Closed for the ordering path. `POST /orders` used to remember an `Idempotency-Key` only in the memory of the process that saw the first attempt, while the `idempotency_keys` table it was meant to use sat unused; a client retrying after a crash, a deploy or against a second instance placed a second order. The key, the claim on it and the stored response are now rows, namespaced with the account and the endpoint so one customer's key can never return another's order, and the claim, the order and the answer are written in **one transaction** — so an attempt that dies part-way leaves nothing behind for a retry to build a second order on. Verified across real processes: a retry from a second process returns the first order, and two processes posting the same key simultaneously produce one order and one `order.id`, not two — held by `tests/orderIdempotencyAcrossProcesses.test.ts`, which starts the built API twice against one database file and races the same key at both, so the claim is re-checked by `npm test` rather than resting on a probe that was run once.
   - Limits that remain. The retention window is one hour, after which the same key value is free again — deliberate for an idempotency key, but it does mean a retry after an hour is a new order. A duplicate of a request that is still in flight is answered `409` rather than with the eventual answer, because that answer does not exist yet; the client retries and then replays. If a writer holds the database for longer than the driver's five-second busy timeout, the loser of that race gets `500` instead of a replay — safe (nothing is placed twice) but worth knowing. The guarantee is per database, like every other piece of state here: processes that do not share one (item 8) do not share idempotency. Expired keys are pruned in the order path at most every ten minutes, so the table grows by one row per order placed and is swept in bulk; nothing depends on that sweep running.
11. **SMS Delivery Confirmation**:
   - OTPs are sent through Greenweb or BulkSMSBD with retries and backoff, but `SENT` (Greenweb) and `202` (BulkSMSBD) only mean the gateway accepted the message for submission. Neither provider exposes a delivery-report API we can rely on, so handset receipt is not tracked; operators confirm delivery in the provider dashboard using the message id recorded for every attempt in `otp_deliveries`, which answers "did the code leave, and what did the gateway say?" but not "did the phone ring?". Those rows are kept for 30 days and pruned with later logins; a delivery-report webhook from the provider is the only way to close the remaining gap.
   - Closed for the half an operator can act on. A customer whose code did not arrive was stuck behind the number's own resend cooldown — 60 seconds, database-enforced, and impossible to wait out on somebody else's behalf — with nothing but the delivery trail to read about it. `POST /admin/otp-challenges/reset` (`otp:manage`, administrators) now lifts that wait, and with `send: true` issues and sends one code through the same gateway and the same trail while the caller is on the line. It lifts the wait and nothing else: the code already in the customer's hand stays valid, the wrong guesses that retired a code stay counted until a fresh one starts, and no reset signs anybody in. A number whose first code never arrived is answered rather than refused (`cleared.hadChallenge: false`), the same `503` a customer's own request gets is answered *before* anything is cleared whenever the platform cannot text anybody, and each call writes one `OTP_CHALLENGE_RESET` audit row naming the administrator, the number, what was lifted and whether a gateway took a code — never the code or the hash it is stored as. What it moves is the row's `lastSentAt`, so a second process or a restart sees the lifted wait with no coordination at all, which is verified across two servers sharing one database.
   - What remains is the reading. There is no route that only *reports* a number's login state: an operator sees it as the answer to a reset, so looking at a stuck challenge means clearing it, and a call that established nothing more than "they were being asked to wait 43 seconds" has already moved something. Nothing here can say whether the code reached the handset either — the bullet above stands — and a reset lifts the per-number wait, not the per-address request limit, so a desk working from one office on behalf of several numbers still shares that budget. A challenge row pruned after 24 hours of inactivity leaves no wait to lift, which the response says plainly, and a forced code replaces whatever the customer was holding: `cleared.codeRetired` names that, but the code it replaced is not kept anywhere an operator can read back, so a customer who reads out a code they received before a reset is reading a dead one.
12. **Login Codes Only Go to Bangladeshi Numbers**:
   - Closed. `POST /auth/otp/request` takes the number from the caller and texts it whether or not an account exists — deliberate, because that is what makes registration possible without enumerating accounts — so the destination was effectively the caller's choice and the bill the platform's. `normalizePhoneNumber` accepted any plausible international number through a fallback (`/^\+[1-9]\d{6,14}$/`); a loopback gateway showed `+919876543210` being dispatched to as `919876543210`, with nothing but the per-address request limit in the way. Only the three Bangladeshi forms (`+8801…`, `8801…`, `01…`, with spaces or dashes) are accepted now, and a number outside them is `400`, the same as any other invalid input. Every account on the platform is a Bangladeshi number, so nothing that worked before stops working; supporting tourists would mean adding numbers back deliberately, not by accident. The per-address request limit still applies on top: 100 a minute per address by default, with a 60-second cooldown per number.
13. **Login Codes Are Now Keyed With the Server Secret**:
   - Closed. A stored challenge held an HMAC keyed by the phone number alone, and the number is public — anyone holding the row (a database file, a backup, a replica) could match it against a guessed six-digit code offline in milliseconds. The key is now `${ENCRYPTION_KEY}:${phone}`, which turns a secret that was validated at startup but never used into the thing that protects stored codes. One effect worth knowing: codes issued by the previous version do not verify against the new key, so a code requested immediately before an upgrade has to be asked for again.
14. **Client Identity Behind a Reverse Proxy**:
   - Closed, with an explicit setting. The API looked only at `req.socket.remoteAddress`, which is the one address in a request a caller cannot choose — correct when the API is exposed directly, and completely wrong behind a reverse proxy: every customer then shared a single rate-limit bucket (100 requests a minute for the whole building), and every row written to `auth_sessions` and `otp_deliveries` recorded the proxy, so the session audit trail answered "which proxy?" instead of "which customer?".
   - `TRUST_PROXY` now names the peers that may be believed: empty (the default, meaning "no proxy", and then `X-Forwarded-For` is ignored entirely), `true`/`all`, the keyword `loopback` for a proxy on the same host, or a comma-separated list of addresses and CIDR ranges (`loopback,10.0.0.0/8,2001:db8::/32`). A value that does not parse stops the boot with a Configuration Error, because a typo would otherwise silently resolve to one of the two extremes — trusting nobody, which quietly buckets every client together, or trusting everyone, which lets any caller name itself. The chosen policy is printed at boot, since a wrong answer here is otherwise invisible: the API looks healthy throughout.
   - What it does: a proxy appends the address it accepted the connection from, so the header reads as "what the client claimed, then what each hop observed". The chain is walked from the server outwards and the rightmost entry that is not itself a trusted hop wins, so anything a client wrote to the left of its own proxy is discarded and the header cannot be used to name yourself or to reset a limit. Verified end to end through a running server: a forged `1.2.3.4, <real client>` chain lands in the real client's bucket and an exhausted bucket stays exhausted when only the claim changes, while a genuinely different client is unaffected. Entries that are not addresses are dropped rather than stored, so a value a caller typed never becomes the address recorded against its own request; IPv4-mapped IPv6 peers (`::ffff:127.0.0.1`) are folded to IPv4 so a dual-stack listener and an IPv4 header entry agree on the same host; and only the hops nearest the server are read from a padded header, so padding cannot push the believable hop out of view.
   - Both header spellings are now understood. `X-Forwarded-For` and RFC 7239's `Forwarded` are the same chain written two ways — the RFC's header groups each hop's observations into one element (`for`, `proto`, `host`) so they can be correlated, which the legacy list cannot do — and `TRUSTED_FORWARD_HEADER` declares which one a deployment's proxies actually maintain: `x-forwarded-for` (the default, so nothing changes silently for an existing deployment), `forwarded`, or `both`. Nobody else gets to choose: reading a header the proxies do not maintain is precisely how a caller names itself, which is why it is configured rather than guessed. Under `both`, two headers that name different clients are a misconfiguration or a forgery and there is no way to tell which, so neither is believed and the request is attributed to the peer — the one answer an attacker cannot turn into someone else's identity. The RFC header is read properly: parameter names are case-insensitive, values may be tokens or quoted strings (which is how an IPv6 address or a host with a port has to be written), a repeated header field is one list, extension parameters are ignored, `proto` is validated as a URI scheme and `host` against the Host grammar, older hops are discarded as before, and the reported `proto`/`host` belong to the element that named the client rather than to a later hop's own view of the connection.
   - Obfuscated identifiers are honoured rather than guessed at. A hop may legitimately decline to disclose its client — `for=_hidden` (which RFC 7239 says SHOULD be the default configuration, and which SHOULD be regenerated per request) or `for=unknown` — and an element that repeats a parameter, or that cannot be read whole, is not something to half-understand. All of those stop the walk at that hop instead of reading past it, so the request is attributed to the proxy: no invented address is stored, and no older, less trustworthy element — the part of the header the walk exists to discard — is promoted in its place. The cost is real and is logged once per process: every client of an obfuscating proxy shares that proxy's rate-limit bucket, and no session row can name a person, which is the proxy's decision to make and the operator's to notice.
   - Limits that remain. Trusting a peer means trusting everything it forwards, so `TRUST_PROXY` must name the proxies that *append* to the header and never a range that contains real clients; `true`/`all` is safe only where no untrusted path to the API exists. The same is now true of the header choice: a deployment that sets `forwarded` while its proxy maintains `X-Forwarded-For` has told the API to believe a header the caller controls, and nothing can detect that from inside a request — it is the one setting here that has to be right. `X-Forwarded-Proto` and `X-Forwarded-Host` are still not read at all, so a deployment on the legacy header gets no scheme or host. Both settings are read at boot and are not reloadable. And it fixes identity without changing the counter beside it, which is now shared and durable (item 7) — the two together are what make one resolved address mean one budget for the whole deployment. One diagnostic was added for the silent failure that prompted this — a request from a host-local peer carrying a forwarded header the configuration does not trust is logged once per process as a warning — but nothing prevents a deployment from leaving `TRUST_PROXY` empty behind a proxy and simply serving all its customers one bucket, which is why the boot log names the policy.

15. **Recorded Client Addresses Now Expire**:
   - Closed, with a window. `auth_sessions.ipAddress` and `userAgent`, the same two fields on `audit_logs`, and `otp_deliveries.ipAddress` are the only places the platform writes down where a request came from. The SMS trail already deleted itself after 30 days, but session and audit rows are kept by design — they are the record that a login happened, that an administrator approved an account, that a session family was burned for reuse — so the address beside those facts accumulated indefinitely. Every login now also runs a sweep, at most once an hour per process and once at boot, that replaces those fields on records whose window has closed with `[redacted]` (`PII_RETENTION_DAYS`, 90 days by default). The boot sweep is what covers a process that restarts rarely, or is handed a restored backup: it applies the window to what is already there instead of waiting for a customer to sign in.
   - What is deliberately not done. The rows are not deleted — the record survives, minus who it was — and `NULL` is left as `NULL` rather than overwritten, so the trail keeps the difference between "no address was recorded" (the seed rows, and every request that carried no metadata) and "we no longer keep it". A session that is still live is never redacted, whatever the window says, because while a device holds a working token its address is the only answer to "where is this signed in from?" — which is what makes the window safe to set below the 7-day refresh lifetime. The sweep is idempotent (a redacted row is not counted again), and it records nothing about itself in the audit trail: the fields such a record would contain are exactly the ones being removed.
   - Limits that remain. Redaction is overdue rather than prompt: it happens on the next login or boot, so a process that neither restarts nor sees a login holds addresses past their window until one of those does happen. The window is read at boot and is not reloadable. `userAgent` is swept on the same rule as the address even though it is the weaker identifier, and the platform's real identifier — the phone number on the account — is not covered by this window at all, so this de-identifies traffic without making an account anonymous. The tables also still grow: dead sessions and audit rows are never deleted, only de-identified, so a deployment that wants them gone entirely needs a purge policy, which is a different decision because it destroys evidence rather than personal data. One table is deliberately not in this sweep: `request_rate_limits` (item 7) is keyed by a digest of the client address rather than the address, so there is nothing in it to redact, and its rows are dropped when their window closes.

16. **Money-Moving Endpoints Are Now Guarded**:
   - Closed for taking and returning money. `POST /orders/:orderId/payments`, `POST /orders/:orderId/cancel` and `POST /orders/:orderId/refunds` all require an `Idempotency-Key` and run through the same durable guard as placing an order, so a retry returns the stored answer (same `payment.id` / `refund.id`, no second row) after a crash, a deploy or from another process. Beyond the key guard, two different keys asking for the same money are refused by the write transaction: the money taken and the money returned are read and written under one `BEGIN IMMEDIATE`, so both cannot see an empty ledger. A partial unique index makes a second `COMPLETED` payment for one order impossible at the database level, and the cancellation policy decides what a customer is owed (100% before acceptance, minus half the items subtotal once the merchant is cooking, refused once the order is out for delivery). Both halves are held by tests, including two real server processes racing the same cancellation and two different keys racing each other (`tests/orderIdempotencyAcrossProcesses.test.ts`, `tests/moneyMovement.test.ts`), where a refund of more than was paid fails the suite.
   - Limits that remain. There is **no payment gateway call**: `bKash`/`Nagad` appear only as method labels, and a guarded action has to be a database write that can be rolled back with its transaction, so an external charge would need an intent-then-confirm shape this code does not have. A gateway's confirmation therefore has to arrive as a request that carries an `Idempotency-Key` — anything that treats "the gateway said so" as a new charge bypasses the guard. One `COMPLETED` payment per order means split or part-payments are not modelled (`payment_reconciliations` and the settlement engine are still unwired). Refund authority is deliberately split: the customer may cancel and be refunded inside the window, an administrator refunds outside it, and an administrator cannot cancel a customer's order through the cancel route. Refunds are summed against the payment, so a refund that fails mid-way has to be recorded as a new one rather than resumed, and nothing expires or prunes `payments`/`refunds` — they are the permanent ledger, unlike `idempotency_keys`, which keeps a key for one hour. A partial refund leaves the payment `COMPLETED` (there is no `PARTIALLY_REFUNDED` status), and `adminService`'s dispute/refund path is still in-memory and separate from these rows, so the two can disagree until it is ported. The unique index on completed payments is created at boot: a database that somehow already held two completed payments for one order would refuse to start rather than keep the double charge quietly — no code path could have written such a row, since only the seed data ever wrote `payments`.
17. **Declared Configuration That Nothing Applies**:
   - `src/config/env.ts` declares keys the runtime never reads: `LOG_LEVEL` (the logger writes every level to stdout), `CORS_ORIGIN` (no CORS headers are sent at all), `JWT_EXPIRES_IN` (access and refresh lifetimes are fixed in code), `APP_NAME`, and `DATABASE_URL` (declared for a PostgreSQL backend with no driver behind it). `.env.example` now marks them as reserved so an operator does not expect them to take effect; the example file previously also named the request limit `RATE_LIMIT_MAX_REQUESTS` while the code reads `RATE_LIMIT_MAX`, which silently left a deployment on the default.

## 3. Developer Onboarding & Maintenance Guidelines

### Coding Standards
- **Strict TypeScript**: No implicit `any`. All API controllers, payloads, and event schemas must be strictly typed.
- **Error Handling**: Use centralized `AppError` class with standardized JSON response envelope `{ success: false, error: { code, message } }`.
- **Unit & Integration Tests**: Test coverage with Jest/Supertest must exceed 85% for pricing, cart discount calculations, and payment callbacks.
